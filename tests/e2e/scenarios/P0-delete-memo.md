# 시나리오: 메모 삭제

- **우선순위:** P0 (필수)
- **대상 화면:** `http://localhost:3000/` (메모 카드, 삭제 확인창)
- **탐색 일시:** 2026-10-16 (Playwright MCP로 직접 수행하여 확인한 동작 기준)

## 우선순위 근거

되돌릴 수 없는 파괴적 동작이라 오삭제 방지(확인창)와 실제 삭제 반영이 모두 보장되어야 한다. 또한 다른 시나리오가 만든 테스트 데이터를 정리하는 수단이므로 테스트 안정성에도 직결된다.

## 목적

삭제 아이콘을 누르면 확인창이 뜨고, **취소하면 메모가 유지**, **확인하면 DB에서 삭제**되어 목록에서 사라지는지 검증한다.

## 사전 조건

- 개발 서버가 `http://localhost:3000`에서 실행 중이다.
- 삭제 대상 메모가 있다. (`P0-create-memo.md`로 `E2E 삭제 {타임스탬프}` 메모를 먼저 만든다. **기존 데이터는 삭제하지 않는다.**)

## 테스트 데이터

| 항목        | 값                                   |
| ----------- | ------------------------------------ |
| 제목        | `E2E 삭제 {타임스탬프}`              |
| 확인창 문구 | `정말로 이 메모를 삭제하시겠습니까?` |

## 단계와 기대 결과

| #   | 단계                                                    | 기대 결과                                                                                              |
| --- | ------------------------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| 1   | 목록에서 `총 N개의 메모` 개수 N을 기록                  | —                                                                                                      |
| 2   | 대상 카드의 삭제 아이콘(`button[title="삭제"]`) 클릭    | `confirm` 다이얼로그가 뜨고 문구가 `정말로 이 메모를 삭제하시겠습니까?`이다. 상세 모달은 열리지 않는다 |
| 3   | 다이얼로그 **취소(dismiss)**                            | 카드가 그대로 남아 있고 `총 N개의 메모`도 그대로다                                                     |
| 4   | 삭제 아이콘을 다시 클릭하고 다이얼로그 **확인(accept)** | 에러 배너가 나타나지 않는다                                                                            |
| 5   | 목록에서 카드가 사라질 때까지 대기                      | 해당 제목의 카드가 사라진다                                                                            |
| 6   | `총 N-1개의 메모` 문구 확인                             | 개수가 정확히 1 감소했다                                                                               |
| 7   | 페이지 새로고침 후 다시 확인                            | 카드가 다시 나타나지 않는다 (DB에서 삭제됨). 개수는 N-1 유지                                           |

## 선택자 (탐색 시 확인한 값)

| 대상        | 선택자                                                                       |
| ----------- | ---------------------------------------------------------------------------- |
| 대상 카드   | `[data-testid="memo-item"]` 중 `h3` 텍스트로 필터                            |
| 삭제 아이콘 | 카드 안 `button[title="삭제"]`                                               |
| 확인창      | `page.on('dialog', …)` — `dialog.message()` 검증 후 `dismiss()` / `accept()` |
| 에러 배너   | `[data-testid="error-banner"]`                                               |

다이얼로그 핸들러는 **클릭 전에 등록**해야 한다. 취소/확인을 각각 다르게 처리하려면 `page.once('dialog', …)`를 클릭마다 등록한다.

## 정리 (Cleanup)

이 시나리오 자체가 정리 절차다. 단, 중간 단계에서 실패하면 대상 메모가 남을 수 있으므로 `afterEach`에서 `E2E ` 접두사 메모가 남아 있는지 확인하고 삭제한다.

## 알려진 주의 사항 (탐색 중 관찰)

- **간헐적 삭제 미반영 1회 관찰:** 탐색 중 한 번, 확인창을 승인했는데 카드가 20초 이상 남아 있었고 새로고침 후에도 DB에 남아 있었다. 같은 조작을 다시 수행했을 때는 정상 삭제(9개 → 8개)되었다. 당시 에러 배너/콘솔은 확인하지 못해 원인은 미확정이다. (개발 서버 재컴파일(HMR) 중 서버 액션 호출 실패 또는 일시적인 DB 오류 가능성)
- 따라서 5번 단계의 대기는 **타임아웃을 넉넉히** 두고, 실패 시 에러 배너 텍스트와 네트워크 응답을 함께 기록하도록 작성한다. 재현되면 별도 버그로 분리한다.
- 삭제 후 `memo_summaries`의 요약 행도 cascade로 함께 삭제된다 (UI에서는 확인할 수 없고 DB 쿼리로 검증).

## 후속 시나리오 후보 (이번 범위 밖)

- 상세 모달(카드 클릭)의 `삭제` 버튼으로 삭제 후 모달이 닫힘
- 삭제 실패(네트워크 오류) 시 에러 배너 표시와 카드 유지
